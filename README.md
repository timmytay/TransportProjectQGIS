## Центроиды зданий по площади

- `building_centroids.py` — из полигонов `data/здания_генерация.parquet` строит центроид каждого здания (центр масс площади, расчёт в UTM 48N) → `data/здания_центроиды.parquet`. Запуск: `python building_centroids.py` (с `--gpkg` дополнительно пишет `exports/здания_центроиды.gpkg` для QGIS). Если файла нет, сервер построит его сам при первом запросе.
- Поля: `area_m2` — реальная площадь пятна здания, `FLOORS`, `weight_area` = `area_m2 × FLOORS` (вес), `inhab`, `inside` — лежит ли центроид внутри контура.
- Эндпоинт `/load-buildings-centroids`, слой «Центроиды зданий 2.0».
- Районирование: в списке «Здания для районирования» выбрать «Центроиды зданий 2.0», выделить область. Центр каждого района (★) = Σ(xᵢ·Sᵢ)/ΣSᵢ, Σ(yᵢ·Sᵢ)/ΣSᵢ, где Sᵢ — площадь здания; k-means тоже пересчитывает центры с весом площади.

## Категории зданий по рубрикам 2ГИС (приоритеты)

Данные руководителя лежат в `data/rubriki/`: справочник 47 категорий, 1652 рубрики → категории, 24 521 организация Иркутска.

- `data/rubriki/prioritety_kategorij.csv` — таблица приоритетов (редактируется):
  `Приоритет` — группа 1..5 (1 транспорт/спецобъекты, 2 крупные центры притяжения, 3 социальные, 4 торговля и услуги, 5 жильё и фон);
  `Ранг` — общий порядок 1..47; `Якорные рубрики` / `Иначе` — для категорий, куда справочник отнёс «лишние» рубрики
  (например, «Авиабилеты» размечены как Аэропорт; без якорной рубрики «Аэропорты» организация получает код из `Иначе`).
- `building_categories.py`: организация → самая приоритетная категория среди ВСЕХ её рубрик → привязка к ближайшему зданию (≤ 30 м) →
  категория здания = самая приоритетная среди его организаций; без организаций, но с жителями — Жильё (SQ1).
- Поля в `здания_центроиды.parquet`: `cat_code`, `cat_name`, `cat_priority`, `cat_group`, `n_orgs`, `cat_source`.
  Выгрузка организаций с итоговой категорией: `exports/организации_с_приоритетом.csv`.
- На карте центроиды раскрашены по приоритету; у центра района — ведущая категория (самая приоритетная) и структура по площади.
- После правки таблицы приоритетов удалите `data/здания_центроиды.parquet` (или запустите `python building_centroids.py`) и перезапустите сервер.

## Профиль зоны по площади (по README руководителя)

- Площадь этажей здания делится между функциями (поле `mix`): есть жители и организации — организациям первый этаж
  (у одноэтажного дома половина), остальное жильё; жителей нет — вся площадь организациям поровну; только жители — жильё.
  Организации без категории — `NA` (нет данных). Поле `org_cats` — число организаций по категориям.
- `data/rubriki/ukrupnenie_kategorij.csv` — укрупнение 47 категорий до функций: Жилая, Торговля и услуги, Деловая,
  Социальная, Отдых и спорт, Производственная, Транспортная, Прочее (исходные коды не меняются).
- У центра района (★): тип зоны (функция ≥ 60 % площади → зона по ней, иначе «Смешанная (A + B)»), доли площади по функциям,
  доля площади без данных, число организаций по категориям, ведущая категория по приоритету.
- Кнопка «Профили районов (CSV)»: доли по функциям, площадь (`S_SQx`) и число организаций (`N_SQx`) по каждой из 47 категорий —
  признаки для кластеризации зон по профилю.

## Барьеры при районировании (исправлено)

Причина, по которой барьеры не разделяли кластеры: линии барьеров обводились буфером ~1 м и полигонизовались —
получались узкие «колбаски» вдоль рек и дорог (на участке центра — 19 штук), в которые попадало 6 зданий из 25 036.
Все остальные здания оказывались в одной группе «снаружи», и k-means делил её, не видя барьеров. Кроме того, линия,
пересекающая область, сама по себе не образует замкнутого полигона, а MultiPolygon-барьеры сервер пропускал.

Сейчас (`POST /api/barrier-faces`, `js/barriers.js`): выделенная область разрезается всеми включёнными барьерами
(границы полигонов + линии, полоса ±5 м, в UTM) на части; каждое здание относится к своей части; k-means и DBSCAN
работают внутри частей; K распределяется между частями (минимум 1 на часть с зданиями, остальное пропорционально
площади этажей, метод Д'Ондта). Если частей больше K — районов будет столько, сколько частей. Полигоны районов
обрезаются по своей части. Линии раздела показываются пунктиром.

## Центры притяжения — модель Хаффа по улично-дорожной сети (по замечанию преподавателя)

Метод «Центры притяжения — крупные объекты» (по умолчанию). Центр района — реальное крупное здание (вуз, ТЦ, больница,
завод, вокзал), к которому «тянутся» окружающие здания. Так строят зоны тяготения в транспортном моделировании:

1. Масса (привлекательность) здания `M = нежилая площадь этажей × коэффициент группы приоритета`
   (1 → 3; 2 → 2,5; 3 → 2; 4 → 1,5; жильё → 0; без данных → 1). Нежилая площадь — из профиля `mix` (всё, кроме SQ1).
2. Центры программа находит сама: здания с `M ≥ порога` (по умолчанию 20 000, поле в панели). Крупные здания ближе
   500 м друг к другу (корпуса вуза, корпуса ТЦ) объединяются в один центр, массы складываются.
3. Каждое здание относится к центру с наибольшим притяжением (модель Хаффа) `A = M / max(d, 100 м)^2`,
   где `d` — кратчайшее расстояние по графу дорог `граф.gpkg` (`POST /api/huff-assign`, алгоритм Дейкстры, scipy);
   если граф недоступен — по прямой.
4. Барьеры: здание тянется только к центру своей части области.
5. Слабые центры (зона тяготения < 50 зданий) отсеиваются, распределение пересчитывается.

Число районов = число найденных центров. Снять флажок «автоматически» — задать K вручную (K самых «тяжёлых» зданий).
Точки района и звезда центра — одного цвета; подписи на карте нет, сведения — по щелчку на звезде.
Константы — в начале блока «ЦЕНТРЫ ПРИТЯЖЕНИЯ» в `js/clustering.js`.

## Запуск без QGIS

Слои (GPX, GPKG, SHP) читаются через GeoPandas (`layer_to_geojson` в `app.py`), координаты переводятся в EPSG:4326,
кодировка shapefile берётся из `.cpg`. QGIS больше не обязательна: если она установлена, используется только как
запасной способ чтения, когда GeoPandas не смог открыть файл (инициализация QGIS — при первой необходимости).
`run_server.bat`: Python из QGIS (если есть) или обычный Python 3.10+; недостающие библиотеки ставит сам (`requirements.txt`).

## Сплошные районы и раскраска (без «разбросанных» точек одного цвета)

* После модели Хаффа районы делаются **сплошными**: здания района должны быть связаны цепочкой
  соседей ≤ 150 м (в одной части между барьерами). Оторванные куски передаются соседнему району,
  с которым у них больше всего общих границ (`_make_contiguous` в `app.py`). Остаются только куски,
  отделённые пустырём, ближайший сосед которых — свой же район.
* Если здание-центр ушло в соседний район, звезда переносится на самое крупное здание своего района.
* Цвета подбираются как на политической карте: **соседние районы — всегда разными цветами**
  (палитра из 8 контрастных цветов; цвет повторяется только у несоприкасающихся районов).

## Рельеф — новый барьер «Рельеф (крутые склоны)»

Данные: цифровая модель рельефа SRTM 1″ (≈30 м), тайлы `N51E102…N52E105.hgt` из командной папки
«проект/rar file/landscapes». Подготовка — `python relief.py` (один раз, результат уже в `data/рельеф`):

* `крутые_склоны.gpkg` — участки с уклоном **≥ 12° (≈21 %)**, площадью ≥ 2 га. Уклон
  α = arctg √((∂h/∂x)² + (∂h/∂y)²); порог 20 % — граница неблагоприятных для застройки и дорог
  территорий (СП 42.13330). Шум SRTM сглажен, мелкие пятна отброшены;
* `dem_2s.npz` — облегчённая модель высот (шаг 2″) для высот зданий и узлов дорожного графа;
* `отмывка.png` — тени рельефа, показываются на карте вместе со слоем;
* в `здания_центроиды.parquet` добавлено поле `elev` — высота здания над уровнем моря.

Как рельеф влияет на районирование (включается галочкой слоя «Рельеф» в барьерах):

1. **Барьер:** склоны вырезаются из области целиком — районы не проходят через склон.
2. **Центры притяжения:** расстояние по дорогам считается как «приведённая длина» по правилу
   Нейсмита: `L' = L + 8·|Δh|` (подъём на 1 м ≈ 8 м пути по ровному). Метод в статусе — «по дорогам с учётом рельефа».
3. **Сплошность районов:** здания, между которыми склон круче 12°, не считаются соседями —
   район не «перетекает» с террасы на террасу.
4. **K-means и DBSCAN:** расчёт в 3D, третья координата `z = 8 · высота` (м), т.е. перепад 10 м
   разделяет здания так же, как 80 м по горизонтали.

## Масштабирование — районы пересчитываются при приближении и отдалении

Галочка «Масштабирование» на панели районирования. Районы строятся для видимой части карты
(в пересечении с выделенной областью, если она есть) и пересчитываются после каждого
приближения / отдаления / сдвига (через 0,7 с после остановки карты). Уровень детализации — по масштабу:

| Масштаб Leaflet | Уровень | Площадь района (k-means) | Порог крупного объекта | Радиус комплекса |
|---|---|---|---|---|
| 12 | планировочные районы | 6 км² | 80 000 | 1200 м |
| 13 | жилые районы | 2,5 км² | 40 000 | 800 м |
| 14 | микрорайоны | 1 км² | 20 000 | 500 м |
| 15 | группы кварталов | 0,35 км² | 8 000 | 300 м |
| 16+ | кварталы | 0,15 км² | 3 000 | 150 м |

Для k-means число районов `K = застроенная площадь в кадре / площадь района уровня`
(застроенная площадь — клетки 100×100 м, где есть здания). Мельче масштаба 12 расчёт не запускается.
**Без галочки работает прежний режим**: выделенная область, своё число районов K или свой порог.
Файл — `js/scale-mode.js`.

### Ровные границы районов
* Здание подключается к дорожной сети в **3 ближайших узлах** (как коннекторы зоны в VISUM):
  `d_ij = min по узлам n (|i n| + путь по графу от n до центра j) + подход центра`. С одним узлом все
  дома вокруг узла получали одинаковые расстояния и районы были «пятнистыми».
* Перед склейкой — модальный фильтр: здание, у которого своих соседей < 3 из 8, а из одного
  другого района ≥ 5, переходит к соседям (3 прохода; здания-центры не меняются).
* Сплошность районов проверяется по графу 8 ближайших соседей (≤ 150 м) — быстро даже на 100 тыс. зданий.
* В палитре красный заменён на коричневый (на мелких точках красный и оранжевый путались).
